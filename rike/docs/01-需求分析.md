## 1. 背景

每天练吉他时，手上其实同时有三件事：

1. 这首曲今天要过多少遍
2. 谱就在眼前，有时要圈个指法、写个记号
3. 忘了某条乐理时，要能马上翻笔记

这三件事现在散落在「脑子里数数 / 相册里的谱 / 备忘录里的截图」。练的时候手在琴上，切 App 的成本很高：谱被缩成一张小图看不清，数着数着忘了第几遍，乐理笔记一打开，谱的位置就丢了。

市面上相关产品也对不上这个缺口：

- **节拍器 / 调音器 App**：解决的是声音，不解决「今天过了几遍」和「谱上的记号」。
- **纯相册 / 文件 App**：谱能存，但不能当练习主画面用，标注是系统批注，和遍数无关。
- **通用待办**：能勾「练吉他」，但勾完没有辅助，等于把问题又丢回给相册。

本项目做第四种：**把遍数、曲谱、乐理绑在「今天练吉他」这一件事上。** 第一期先服务自己；形态是能扫码打开的手机网页，等小程序账号下来再迁。

## 2. 问题定义

用一句话写问题（企业里常叫 problem statement）：

> 练吉他时，曲谱、遍数、乐理笔记是三件分开的东西；练习过程中无法在同一块屏幕上完成「看谱、涂写、计数、翻笔记」。

把这句话拆开，是三个必须一起解决才闭环的问题：

| 编号 | 问题 | 发生时机 | 不解决会怎样 |
|---|---|---|---|
| P1 | 目标遍数因曲而异，过完一遍要立刻记上一笔 | 正在弹，手刚离开琴 | 靠脑子数，数丢了；或掏手机开备忘录，打断练习 |
| P2 | 曲谱必须是练习的主画面，还要能写记号 | 对着谱反复过同一段 | 缩略图看不清；系统相册的标注和谱是分开的两张图 |
| P3 | 卡住时要立刻温习乐理，但不能离开谱 | 某小节的节奏 / 和弦记不清 | 切到笔记 App，回来谱已经滚到别处，计数也乱了 |

只做计数器，这是个计次器。  
只做看图，这是个相册。  
三件绑在「今天练这一首」上，才是日课。

## 3. 用户是谁

第一期只有一类用户。

| 角色 | 是谁 | 第一期要不要服务 |
|---|---|---|
| 主用户 | 站点主人自己（每天练吉他、谱是图片、会自己拍乐理笔记） | 要 |
| 访客 | 想用别人的谱、看别人练了多少遍 | 不要 |
| 老师 / 陪练 | 远程布置作业、看完成情况 | 不要 |

第一期按「单用户、私人工具」设计。不为多账号、社交、公开主页做预留界面。数据形状不要把「只有吉他这一种任务」写死成无法扩展，但产品行为必须按吉他练习来。

## 4. 用户场景

企业里写场景，是为了后面做功能时能对照：这个按钮到底服务哪一次使用。

### 场景 A：开始今天的练习（对应 P1）

用户坐下，拿出琴。打开日课，看到今天过了几遍、目标是多少。目标不对就改一下（今天这首只要 8 遍，明天换曲改成 20）。

**成功**：3 秒内知道「今天还差几遍」，手可以回到琴上。

### 场景 B：对着谱过一遍（对应 P1 + P2）

谱铺满屏幕。用户弹完一遍，腾出一只手指点一下。计数 +1。谱上要圈指法时，能直接涂，缩放、拖动不丢那些记号。

**成功**：不用退出看谱，就能完成「过一遍」和「写个记号」。

### 场景 C：卡住了，翻乐理（对应 P3）

某小节的三连音规则忘了。用户点笔记，看到自己存的乐理图，看完关掉。谱还在刚才那一页、刚才那个缩放，遍数没变。

**成功**：温习不超过 30 秒，练习上下文全部还在。

### 场景 D：今天练完了

遍数到达目标。界面明确说「今日练习吉他已完成」。用户如果还想再过两遍，可以继续点，完成态保持。

**成功**：不是静默停在 20/20，而是有一句完成语；也不因为完成了就把按钮锁死。

### 场景 E：第二天

新的一天打开，遍数从 0 开始，目标还是昨天设的那个。曲谱、笔记、标注都还在。

**成功**：跨日清的是「今天练了几遍」，不是「我的谱和目标」。

## 5. 第一期做什么

对应三个问题，第一期只做能闭环的最小集。

| 编号 | 需求 | 对应问题 |
|---|---|---|
| R1 | 自定义目标遍数，默认一个合理数字，随时能改 | P1 |
| R2 | 点一下 +1；误触可 −1；低于 0 不再减 | P1 |
| R3 | 到达目标展示「今日练习吉他已完成」；允许超额 | P1 |
| R4 | 按本地日历日跨日清零遍数，目标保留 | P1 |
| R5 | 上传曲谱图片，支持一首多页 | P2 |
| R6 | 曲谱占满屏幕，可拖动、双指缩放、按钮缩放 | P2 |
| R7 | 可手写标注（画笔、换色、粗细、橡皮、撤销、清空本页），标注跟谱走 | P2 |
| R8 | 练谱时有计数入口，不必退回首页 | P1 + P2 |
| R9 | 乐理笔记：另一组图片，可增删浏览 | P3 |
| R10 | 练谱中随时打开笔记覆盖层，关掉不丢谱的状态 | P3 |
| R11 | 同一浏览器刷新、关掉再打开，数据还在 | 全部 |
| R12 | 部署为 GitHub Pages，扫码即可在手机打开 | 形态 |

## 6. 第一期明确不做什么

提出来很合理、但第一期做会炸范围的，写在这里挡回去。

| 不做 | 为什么现在不做 |
|---|---|
| 真微信小程序 | 账号和审核周期与「先能练起来」无关；页面按小程序习惯拆，以后再迁 |
| 登录 / 多设备同步 | 没有账号却要求换手机数据还在，等于偷偷做云；第一期只验同一浏览器 |
| 任务列表、自己新建任务 | 那是二期「全能待办」的产品，不是第一期的吉他练习 |
| 自己拼辅助页面（部件编辑器） | 第一期三个部件写死在吉他任务上；数据留门，界面不盖楼 |
| 画画打卡、日历热力图、进步时间线 | 属于二期另一种完成规则 |
| 节拍器、调音器、录音 | 解决的是另一个问题，会把主路径挤歪 |
| 云端、多人、老师布置作业 | 没有主用户自己用起来的闭环之前，不做给别人看的功能 |
| 识别曲谱、自动翻页、MIDI | 研究型能力，不是第一期用户场景 |

## 7. 怎样算第一期成功

产品成功，不是「功能都做了」，是场景能走完：

1. 用户能在手机上扫码打开，不用开电脑。
2. 对着谱练 20 分钟，只靠这一个页面完成计数、看谱、涂写、翻笔记。
3. 第二天打开，遍数归零，谱和笔记还在。
4. 清微信缓存会丢数据——这是已知限制，不是第一期缺陷；要有导出备份的退路（P1，见 PRD）。

## 8. 和二期的关系（先懂，不先做）

用户后续想做成「不局限于勾任务，每个任务可以自定义辅助页」：练吉他是曲谱 + 计数；画画是上传成果 + 日历。

企业里这句话叫 **组合，不要为每个任务定制一页**。

抽象是：

> 一个任务 = 怎么算完成 + 一组辅助部件。

第一期只实例化「练习吉他」这一条：完成规则是每天计数达到 N，部件是计数器、曲谱画板、笔记。  
数据按任务 / 资源角色来存，界面先做成吉他这一套。二期再打开「新建任务 + 勾选部件」，而不是推翻重写。

需求分析到此为止。做成什么样，见 PRD。
