## 1. 背景

发朋友圈时，经常是「图已经有了，句子卡着」。平时偶尔会冒出一句合适的话，但当时没有地方快速记；等真要发圈，又翻不到，最后要么硬憋，要么发一张没文字的图。

市面上已有两类产品，都对不上这个缺口：

- **文案合集 App**：海量通用句子，抄起来快，但不是自己的语气。
- **看图生成文案**：模型现写一段，容易像鸡汤，不像自己会发的话。

本项目做第三种：**把用户自己攒下的金句，在发圈那几十秒里，对上眼前这张图。**

---

## 2. 问题定义

用一句话写问题（企业里常叫 problem statement）：

> 用户平时冒出的金句没有可靠的收录入口；发圈时面对已有照片，无法在自己的句子里快速找到最合适的一条。

把这句话拆开，其实是两个问题，必须一起解决才闭环：

| 编号 | 问题 | 发生时机 | 不解决会怎样 |
|---|---|---|---|
| P1 | 金句稍纵即逝，记下的成本太高 | 走路、洗澡、刷到一句很准时 | 库是空的，后面匹配没有原料 |
| P2 | 发圈时图和文案对不上 | 已经打开相册、准备发了 | 有库也用不上，产品不会被打开 |

只做收录，这就是个备忘录。  
只做匹配、没有库存，匹配再聪明也没有句子可推。

---

## 3. 用户是谁

第一期只有一类用户。

| 角色 | 是谁 | 第一期要不要服务 |
|---|---|---|
| 主用户 | 站点主人自己（有发朋友圈习惯、会随手攒句子） | 要 |
| 访客 / 投稿者 | 想抄别人金句、或上传给别人用的人 | 不要 |
| 运营 / 审核 | 管公共库质量的人 | 不要 |

第一期按「单用户、私人工具」设计，不为多账号、社交、公开页做预留界面。数据上只要不把「仅自己可见」写死成无法扩展即可，产品行为必须按私人库来。

---

## 4. 用户场景

企业里写场景，是为了后面做功能时能对照：这个按钮到底服务哪一次使用。

### 场景 A：灵感出现了（对应问题 P1）

用户突然想到一句，或看到一句想留着以后发。此时他不想分类、不想命名、不想填表，只想 30 秒内把句子留下。

**成功**：句子进库了。分类可以事后再改，也可以交给系统先标。

### 场景 B：准备发朋友圈了（对应问题 P2）

用户相册里已经有图，需要 1～3 行配文。他希望上传图片后马上看到几条「比较适合这张图」的自己的句子，点一下就能复制。

**成功**：30～60 秒内复制到一条愿意发的句子。

### 场景 C：匹配不准，但还是要发

图片很普通，或库里没有足够贴合的句子。用户不能看到空白页，需要能按相关分类把句子划完，自己挑。

**成功**：至少能开始浏览，而不是卡住。

### 场景 E：不配图，只发圈

用户有时只想发一句，没有图，或不想用「按图配文」。此时应能在「片语」列表里直接复制。

**成功**：在列表上点「复制」，不必先传图。

### 场景 D：系统分错类

自动分类把一句励志标成了美食。用户能改，改完以后这句按新分类参与匹配。

**成功**：改分类的成本是「点一下」，不是重新录入。

## 5. 目标与非目标

这一节是需求分析里最值钱的部分。范围不锁死，后面每个人都会往里塞功能。

### 第一期要达到的目标

1. 能极速收录金句，不打断思路。
2. 每条金句有「场景 × 情绪」两轴标签；系统先标，用户能改；标不准则归入「其他」。
3. 上传一张图片，从**个人库**里给出最合适的若干条文案。
4. 匹配没把握时，自动降级到相关分类的全部文案，供用户划选。
5. 选中的句子能一键复制。

### 第一期明确不做

| 不做 | 原因 |
|---|---|
| 多人注册、公开库、投稿、点赞评论 | 已拍板：先做自己的库 |
| 根据图片生成全新文案 | 会变成通用鸡汤，和「用自己的句子」冲突 |
| 根据文案生成配图 / 海报排版 | 那是设计工具，不是本产品 |
| 自动发到微信朋友圈 | 做不到，也不该做 |
| 一次上传九宫格并分别配文 | 第一期先闭环「一张图」 |
| 复杂搜索、文件夹、多本库 | 个人库前期用不到 |

## 6. 分类规则（已拍板）

不用一棵很深的分类树。金句经常跨类，单标签会又错又难改。

采用两轴，一条金句 = **1～2 个场景 + 1 个情绪**。

### 场景（描写「图/事发生在哪类生活里」）

1. 旅行
2. 美食
3. 风景自然
4. 日常生活
5. 人物自拍
6. 宠物
7. 夜色城市
8. 工作学习
9. 节日纪念日
10. 其他

### 情绪（描写「发这句话时想传递的感觉」）

1. 松弛治愈
2. 浪漫暧昧
3. 幽默俏皮
4. 孤独丧
5. 热血励志
6. 冷淡高级
7. 珍惜感恩
8. 其他

### 归类策略

- 系统先自动打标签，并带一个「有没有把握」的判断。
- 有把握：直接写入，录入过程不打断用户。
- 没把握：场景或情绪落在「其他」，可附带 1～2 个建议，用户点一下就能改。
- 用户手动改过的标签，优先级高于系统标签。
- 「其他」只表示「这一轴现在不确定」，不是一个真正的内容类别。两轴都确定时，不要随手标其他。

## 7. 图文匹配规则（产品层）

这里只定「用户应该感受到什么」，不定模型怎么训。

### 原则

1. **只从个人库里找**，不写新句子。
2. **先看场景和情绪，再比较句子意思**。图里是咖啡，不等于只能配「咖啡」两个字的句子；但图是夜景，就不该把「周末早午餐」放在第一位。
3. **永远给结果**。没有「匹配失败，请重试」。
4. **推荐不是唯一答案**。界面表达应是「比较适合这张图的几句」，不是「已为你匹配到唯一文案」。
5. **刚用过的句子降低优先级**，避免连续两天推同一句。

### 降级策略（必须写进需求，否则开发会做成空页面）

| 把握程度 | 用户看到什么 |
|---|---|
| 高 | 置顶 3 条最配的 + 一句很短的原因（如「夜景 · 松弛」） |
| 中 | 3 条候选 + 可以进入附近分类继续看 |
| 低 / 库太小 / 对不上 | 直接进入相关分类的全部文案，按最近收录、最近用过排序，方便遍历 |

库很小（例如不足约 20 条）时，浏览往往比「假装很准的匹配」更有用。产品上允许：库小时更早进入分类浏览，同时仍给出它认为最接近的几条。

### 图片隐私

朋友圈照片是生活现场。第一期默认：**匹配用完不长期保存原图**。句子库要保存，照片不是资料库。

## 8. 需求清单与优先级

优先级按企业常用的 P0 / P1 / P2：

- **P0**：没有它，第一期不能叫做成
- **P1**：有了会明显更好，可以第一期后半段做
- **P2**：明确知道要，但第一期不做

| ID | 需求 | 优先级 | 对应场景 |
|---|---|---|---|
| R1 | 录入金句（正文必填） | P0 | A |
| R2 | 自动打「场景 × 情绪」；不准则「其他」 | P0 | A、D |
| R3 | 用户改分类 | P0 | D |
| R4 | 查看、编辑、删除自己的金句 | P0 | A、C |
| R5 | 按场景 / 情绪筛选浏览 | P0 | C |
| R6 | 上传 1 张图片，从个人库匹配文案 | P0 | B |
| R7 | 匹配没把握时降级到分类浏览 | P0 | C |
| R8 | 一键复制文案（配图页与片语列表都要有） | P0 | B、C、E |
| R9 | 展示匹配理由（短标签即可） | P1 | B |
| R10 | 记录使用次数 / 上次使用，避免刚用过的再置顶 | P1 | B |
| R11 | 「换一批」或切换情绪/场景后重新筛选 | P1 | C |
| R12 | 把已选金句按当前图片微改半句 | P2 | 不做 |
| R13 | 公开分享、多人投稿 | P2 | 不做 |
| R14 | 九宫格、生成配图、发到微信 | P2 | 不做 |

## 9. 成功标准

第一期不看注册人数（只有自己），看有没有进入真实使用。

| 类型 | 标准 |
|---|---|
| 主成功 | 主人至少有一次：用本产品复制文案，并真实发到朋友圈 |
| 收录 | 灵感出现时，能在约 30 秒内完成保存 |
| 出图 | 有图有库的情况下，1 分钟内能复制到一条愿意用的句子 |
| 失败兜底 | 匹配再差，也不能出现空结果页 |
| 分类 | 用户改分类的路径存在，且改完影响后续匹配 |

不作为第一期考核的：匹配「绝对准确」、金句数量、有没有分享给朋友。

## 10. 约束、假设、风险

### 假设（先当它成立，后面如果破了要回来改需求）

- 第一期只有一个主人使用。
- 主人愿意先攒一批句子；库是空的时候，匹配价值接近于零。
- 使用场景以手机为主，桌面为辅。
- 用户最终是把文案粘到微信里发，本产品不接管微信。

### 约束

- 第一期不做账号体系也可以先跑通（单机/单用户），但句子数据必须能留下来：同一浏览器刷新、关掉再打开不能当没发生过。换浏览器、换设备第一期不保证（无登录做不到稳定同步）。
- 自动分类和看图匹配依赖模型，会错。产品必须按「会错」来设计，而不是按「模型很准」来设计。
- 不长期保存用户上传的朋友圈原图。

### 风险

| 风险 | 影响 | 第一期怎么处理 |
|---|---|---|
| 图文意境匹配不准 | 用户觉得「推荐乱」 | 降级浏览 + 文案表述为「比较适合」 |
| 分类体系不合适 | 用户懒得改，匹配更乱 | 先用本表两轴；真不够用再加，不提前做很深的树 |
| 库太小 | 匹配没有原料 | 收录必须比匹配更早可用；库小时偏浏览 |
| 范围膨胀成社区 | 做不完、库变脏 | 非目标表卡住，评审时挡需求 |

---

## 11. 结论

建议立项进入下一阶段：**写 PRD（产品需求文档）**。

下一份文档要在本分析的边界内，把第一期 P0/P1 写成「页面上有什么、主流程怎么走、异常怎么处理」。还不写代码，也不选框架。

待评审确认的拍板（已在需求讨论中确认，写入本文作锁定）：

1. 分类采用「场景 × 情绪」两轴，本表类目作为 v1。
2. 第一期严格个人库，不做公开与投稿。
3. 匹配失败必须降级到分类浏览，禁止空结果。
4. 不生成全新文案，只检索已有金句。
